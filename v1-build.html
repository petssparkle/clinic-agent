V1 Build Playbook · Engineering only · Kickoff: Jun 15, 2026

How we build V1 with Claude & Claude Code.

Pure engineering — no marketing, no acquisition, no GTM. Just the stack, the schema, the API integrations, the code patterns, and the sprint-by-sprint walkthrough that turns the 4 pillars (Unified Inbox · AI Chatbot · Calendar · Mini CRM) into shipping software. Everything starts Jun 15 — accounts, Meta approvals, repo, code. Approvals take 2–4 weeks each, so we file them on Day 1 and code around them while they land.

00What we're shipping in V1

Lock these four pillars in your head — every build decision below maps back to one of them. If a feature doesn't map, it's V2.

Pillar 1 · Unified Inbox

  • WhatsApp + Instagram + Messenger + TikTok in one view
  • Inbound webhook receiver per channel
  • Send replies from one UI, any channel
  • Threading per customer (one thread, all channels)
  • Private notes + @-mentions + quick-reply templates

Pillar 2 · AI Chatbot

  • Fixed-reply mechanic — bot only sends what the business wrote
  • Intent classifier (Claude API) on every inbound message
  • FAQ Library editor in the dashboard
  • Setup Wizard to populate it (services, prices, hours, FAQs)
  • Human handoff when intent doesn't match

Pillar 3 · Calendar

  • Native booking calendar (working hours, slot rules, no double-booking)
  • Bot pulls free slots when customer signals booking intent
  • Customer picks → appointment created → confirmation sent
  • Pre-appointment reminders (timing set by business)
  • Email notification to owner on every booking

Pillar 4 · Mini CRM

  • Auto-pull every inbox message into a Contact record
  • Tags (auto + custom) · Notes (private) · Status
  • Conversation history per contact, across all channels
  • Custom Follow-Up Rules (no-code trigger → reply → delay)
  • Basic analytics (6 counters)
That's the whole V1. 17 features clustered around 4 pillars. Anything not on this page is V2 or later — no exceptions.

03Database schema — the V1 data model

Lock this in Week 2. Everything else builds on top of it. Multi-tenant from Day 1 — each business is a Workspace; every row is scoped by workspaceId.

// Prisma schema — V1 core tables (simplified)

model Workspace {
  id            String   @id @default(cuid())
  name          String
  plan          Plan     @default(STARTER)  // STARTER | GROWTH | AGENCY | ENTERPRISE
  contactsLimit Int      @default(500)
  createdAt     DateTime @default(now())
  users         User[]
  contacts      Contact[]
  // ... all other tables FK back to workspaceId
}

model User {
  id          String     @id @default(cuid())
  workspaceId String
  email       String     @unique
  name        String?
  role        UserRole   @default(MEMBER)
  workspace   Workspace  @relation(fields: [workspaceId], references: [id])
}

model Contact {
  id           String         @id @default(cuid())
  workspaceId  String
  name         String?
  phone        String?
  channelIds   ChannelLink[]  // WA / IG / Messenger / TikTok handles
  tags         Tag[]
  status       ContactStatus  @default(NEW)  // NEW | ACTIVE | BOOKED | CHURNED
  source       String?        // "Instagram Ad" | "Walk-in" | etc.
  createdAt    DateTime       @default(now())
  conversations Conversation[]
}

model Conversation {
  id          String     @id @default(cuid())
  workspaceId String
  contactId   String
  channel     Channel    // WHATSAPP | INSTAGRAM | MESSENGER | TIKTOK
  status      ConvStatus @default(OPEN)  // OPEN | HANDED_OFF | CLOSED
  contact     Contact    @relation(fields: [contactId], references: [id])
  messages    Message[]
  notes       Note[]
}

model Message {
  id             String      @id @default(cuid())
  conversationId String
  direction      Direction   // INBOUND | OUTBOUND
  body           String
  channel        Channel
  intent         String?     // classified intent (pricing, hours, booking, etc.)
  sentByAI       Boolean     @default(false)
  sentAt         DateTime    @default(now())
}

model Note {  // private internal notes on conversations
  id             String   @id @default(cuid())
  conversationId String
  authorId       String
  body           String
  createdAt      DateTime @default(now())
}

model Reply {  // the Fixed-Reply FAQ Library
  id           String   @id @default(cuid())
  workspaceId  String
  intent       String   // matches Message.intent
  body         String
  language     String   @default("en")  // "en" | "ar"
}

model Tag {
  id          String    @id @default(cuid())
  workspaceId String
  label       String
  contacts    Contact[]
}

model BookingSlot {  // calendar — generated working-hours slots
  id          String   @id @default(cuid())
  workspaceId String
  startAt     DateTime
  endAt       DateTime
  status      SlotStatus // AVAILABLE | BOOKED | BLOCKED
}

model Appointment {
  id          String      @id @default(cuid())
  workspaceId String
  contactId   String
  slotId      String
  status      ApptStatus  // CONFIRMED | RESCHEDULED | NO_SHOW | COMPLETED
  reminderSent Boolean    @default(false)
}

model Rule {  // Custom Follow-Up Rules
  id          String   @id @default(cuid())
  workspaceId String
  trigger    Json     // { type: "no_booking_within", hours: 24, askedAbout: "price" }
  replyId    String   // FK to Reply
  enabled    Boolean  @default(true)
}
Why this shape: Contact is the CRM root. Conversation groups Messages by channel. Reply is the bot's library. Rule + Appointment cover lifecycle. Note + Tag are the team-collab surface. Every table FKs to workspaceId — that's the entire multi-tenancy model.

// app/api/webhooks/whatsapp/route.ts
export async function GET(req: NextRequest) {
  const p = req.nextUrl.searchParams;
  if (p.get('hub.mode') === 'subscribe'
      && p.get('hub.verify_token') === process.env.META_VERIFY_TOKEN) {
    return new NextResponse(p.get('hub.challenge'), { status: 200 });
  }
  return new NextResponse('forbidden', { status: 403 });
}

export async function POST(req: NextRequest) {
  const body = await req.json();
  const change = body.entry?.[0]?.changes?.[0]?.value;
  const msg = change?.messages?.[0];
  if (!msg) return NextResponse.json({ ok: true });

  await ingestMessage({
    channel: 'WHATSAPP',
    externalId: msg.id,
    from: msg.from,
    body: msg.text?.body,
    phoneNumberId: change.metadata.phone_number_id,
  });
  return NextResponse.json({ ok: true });
}

Week 5
AI Chatbot — intent classification + fixed-reply matching
  • On every inbound message: classify the intent with Claude API against the workspace's Reply library
  • If matched → fetch the matching Reply for that intent + language, send it back via the channel connector, mark Message.sentByAI = true
  • If no match → don't reply, flag conversation as HANDED_OFF, notify owner (email + dashboard badge)
  • Track all classifications in a ClassificationLog table so we can tune the prompt over time
// lib/ai/classifyIntent.ts
import Anthropic from '@anthropic-ai/sdk';
const claude = new Anthropic();

export async function classifyIntent(
  message: string,
  library: Reply[]
): Promise<{ intent: string; confidence: 'high' | 'low' }> {
  const intents = library.map(r => r.intent).join(', ');
  const result = await claude.messages.create({
    model: 'claude-sonnet-4-6',
    max_tokens: 64,
    system: `You classify customer DMs into ONE of these intents: ${intents}.
Reply with ONLY the intent name. If none match clearly, reply HANDOFF.
The customer's message may be in English or Arabic — handle both.`,
    messages: [{ role: 'user', content: message }],
  });
  const intent = result.content[0].type === 'text'
    ? result.content[0].text.trim().toUpperCase()
    : 'HANDOFF';
  return {
    intent,
    confidence: intent === 'HANDOFF' ? 'low' : 'high',
  };
}

// app/api/cron/reminders/route.ts
export const dynamic = 'force-dynamic';

export async function GET(req: NextRequest) {
  if (req.headers.get('authorization') !== `Bearer ${process.env.CRON_SECRET}`)
    return new NextResponse('unauthorized', { status: 401 });

  const due = await db.appointment.findMany({
    where: {
      reminderSent: false,
      status: 'CONFIRMED',
      slot: { startAt: { lte: hoursFromNow(24) } },
    },
    include: { contact: true, slot: true, workspace: true },
  });

  for (const appt of due) {
    await sendWhatsAppTemplate({
      workspaceId: appt.workspaceId,
      to: appt.contact.phone!,
      template: 'appointment_reminder',
      vars: [appt.contact.name ?? '', formatDate(appt.slot.startAt)],
    });
    await db.appointment.update({
      where: { id: appt.id }, data: { reminderSent: true },
    });
  }
  return NextResponse.json({ sent: due.length });
}

05How we use Claude & Claude Code — the workflow

Two distinct roles. Don't confuse them.

Claude (chat) — the architect

  • Use it for planning, design, prompts, debugging strategy
  • Talk through schema decisions before writing migrations
  • Get second opinions on tricky API contracts
  • Generate prompts that Claude Code will then execute
  • Write product copy, FAQ-library seed content, marketing pages

Claude Code — the builder

  • Use it for actually writing the code — components, API routes, migrations, tests
  • Hand it the Prisma schema + the sprint task — it builds the feature
  • Run it in your terminal, point at the repo, let it iterate
  • Use it for refactors when scope shifts
  • Pair on every PR — write the prompt clearly, review the diff carefully

The per-feature prompt pattern

Every feature ships in 3 steps:

Step 1 — Plan with Claude (chat): "Here's the V1 spec section for the booking calendar (paste §03 + sprint Week 5). What's the simplest implementation? Walk me through the file changes."

Step 2 — Build with Claude Code: "Implement the booking calendar feature per this plan: [paste the plan from Step 1]. Repo conventions: Next.js App Router, Prisma, shadcn. Test it with a Playwright e2e flow."

Step 3 — Review the diff: human reads every file Claude Code touched, runs the test, asks for fixes if needed. Never merge a Claude Code PR without reading it.

What humans do that Claude Code doesn't

  • Customer conversations — Belal + Mahmoud personally onboard the first 20
  • Decisions — schema shape, pricing, feature cuts, what's V1 vs V2
  • Reviewing every diff — Claude Code is fast but not infallible
  • Meta API approvals — the slowest part of V1 is paperwork, not code
  • Demos + sales — humans sell to humans
Honest expectation: Claude Code probably ships 70–80% of the V1 codebase. The remaining 20–30% is human glue — schema decisions, prompt tuning, the actual onboarding UI being perfect, debugging weird Meta API edge cases. Plan for both.
