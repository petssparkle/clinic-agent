01Current Product Understanding

If a new founding engineer joined tomorrow, this is what they need to know.

Product vision

An omnichannel customer-conversation platform for SMBs globally. The product mirrors Respond.io's three-pillar frame (Capture · Convert · Retain) but is built simpler, cheaper, and with a real built-in booking calendar that Respond.io / Trengo / Omnichat all lack as a first-class feature, and that Kommo only ships as Beta.

Sold via four headline pillars: Unified Inbox · AI Chatbot · Calendar & Booking · Mini CRM. The defining mechanic of the AI chatbot is "fixed-reply" — the bot can only send pre-approved replies the business wrote itself. No hallucinations, no off-script.

Business model

  • SaaS subscription, 4 tiers, true monthly billing (not Kommo's 6-month minimum)
  • Starter $15 (Inbox + CRM only) · Growth $59 (+ AI Chatbot + Calendar) · Agency $199 (+ scale, +10 seats) · Enterprise Custom (+ white-label resale)
  • 14-day free trial, no card required
  • Annual billing −20%
  • Contact-pack top-ups for over-quota months
  • Per-workspace, not per-user (Kommo / Trengo / ControlHippo all charge per-seat — our biggest pricing wedge)
  • WhatsApp messaging fees go customer-direct to Meta (BYO WABA model); we pay $0

Target users

SMBs with DM volume + a booking workflow. Vertical-agnostic, but the first 20 customers will mostly come from the founders' MENA warm network: aesthetic/dental clinics, retail, tutoring, auto-service, real-estate brokers, photographers, travel agencies.

The ICP buyer: business owner, age 28–55, runs 50–500 DMs/week, has 1–10 employees, currently uses WhatsApp + Instagram personally / via a receptionist / via a $25–$120/user/mo tool they outgrew. Triggers: after-hours inquiries going cold, 2nd receptionist hire, ad spend leaking to slow replies, no-show rate climbing.

Core workflows (Day 1)

  • Capture: customer DMs on WA / IG / Messenger → webhook ingests → Contact + Conversation auto-created in Mini CRM
  • Convert: Claude classifies intent → matches Fixed-Reply Library → sends back via same channel → if no match, hands off to human
  • Book: "I want an appointment" intent → bot pulls free slots from Calendar → customer picks → Appointment created → reminder cron sends 24h pre + email to owner
  • Retain: Custom Follow-Up Rules cron fires win-back replies for stalled conversations

Current architecture

  • Frontend / API: Next.js 14 (App Router) + TypeScript + Tailwind + shadcn/ui · single repo · Vercel
  • Auth: Clerk (multi-tenant via Workspace model)
  • DB: Postgres on Neon, accessed via Prisma
  • AI: Anthropic Claude API (intent classification, future AI Reply Wand)
  • Channels: Meta Cloud API (WhatsApp), Instagram Graph API, Messenger Platform — TikTok deferred to V1.1 per recommendation §02 below
  • Email: Resend (transactional + reminders)
  • Jobs: Vercel Cron for scheduled work; Inngest / Trigger.dev still to be picked
  • Billing: Stripe + Tap (Gulf) — live mid-July post-incorporation
  • Observability: PostHog (product analytics) + Sentry (errors)

Implementation progress

~0% code, 100% planning. Today is pre-kickoff. Build starts Jun 15, target Sep 1 launch. The current asset is two docs:

  • Main plan (index.html) — business plan, competitive landscape, pricing, acquisition, financials, equity
  • V1 Build Playbook (v1-build.html) — engineering-only: tech stack, schema, 11-week sprint, code snippets per sprint

Validation phase is closed (week-1 competitor trials → joint read-out done; need-validation marked ✓). Next concrete deliverable: Belal files Meta approvals + bootstraps the Next.js repo on Jun 15.

02Critical Review

What I'd push back on if I were on the founding team. Honest, not exhaustive. Sorted by severity.

Critical — fix before Jun 15

  • C1 · Drop TikTok Business Messaging from V1. It's the newest and least documented of the 4 channels, the API quirks will eat 3–5 dev-days, and the marginal user value over WA + IG + Messenger is small for a Sep-1 ship. Move to V1.1. Channel-connector abstraction makes this a one-line add later.
  • C2 · Define "billable contact" precisely. The contact-count metric drives the entire pricing tier ladder ($15 = 500, $59 = 2,000, $199 = 5,000). Right now it's vague. Recommended definition: "A billable contact = a unique person whom the workspace has sent at least one outbound message to during the current calendar month." Inbound-only contacts (people who DM'd you but you never replied to) don't count. This avoids penalizing customers for spam / wrong-number traffic.
  • C3 · Setup Wizard is the single biggest churn risk. A blank FAQ Library kills the bot, kills the value, and the SMB owner uninstalls inside 7 days. Make vertical presets mandatory (not optional) — the wizard ships pre-filled with 12–15 starter replies per vertical (clinic / retail / education / auto / real-estate / pro-services / travel) which the owner only edits. Target self-serve setup time: under 20 minutes, not 60.
  • C4 · Multi-tenancy needs Postgres Row-Level Security, not just middleware filtering. Belal will move fast with Claude Code. One forgotten where workspaceId = ... = a tenant-leak bug. RLS at the DB level is defense-in-depth and cheap to add at schema-init.
  • C5 · No real-time layer in the inbox. If a new DM lands and the agent's UI doesn't update without F5, the inbox feels broken vs Respond.io / Kommo. V1 minimum: SWR polling every 5–10s on the open conversation. V1.1 upgrade: WebSocket via Pusher / Ably / Supabase Realtime.
  • C6 · Webhook idempotency is missing from the schema. Meta retries 5xx responses every few seconds. Without a WebhookDelivery table keyed by (channel, externalId) UNIQUE, a slow DB write = the same inbound message gets ingested 3× = duplicate messages in the UI = embarrassing demos.

Important — design Jun 15–30, ship by Week 6

  • I1 · Plan-feature gating must be server-enforced. Currently implied UI-only. Without server-side gating, a curl request to the chatbot endpoint from a Starter account = free Growth-tier features. Define a PlanFeatures matrix as code and enforce in middleware on every route.
  • I2 · Demo data + guided first-run experience. A brand-new workspace currently lands on an empty Inbox. That's the worst first-impression in SaaS. Seed a guided demo conversation that walks them through inbox → reply → tag → book in 90 seconds.
  • I3 · Calendar needs timezone handling from Day 1. Schema must store BookingSlot.startAt in UTC + Workspace.timezone (IANA). Otherwise a Cairo clinic + a Toronto patient = chaos. This is 30 minutes of work upfront and a week of pain to retrofit.
  • I4 · Outbound message queue + retry. WA send fails happen (rate limits, transient Meta errors). Without a retry queue, a missed reply = a lost lead. Use Inngest / Trigger.dev for outbound queueing — pick one before Week 2.
  • I5 · File / image attachment storage missing. Customers send images on WA constantly (before/after photos for clinics, product pics for retail). No mention of R2 / S3 + signed URLs. Add Cloudflare R2 in W3 (free egress vs S3).
  • I6 · GDPR + data retention. Personal data flows from Day 1. Need: privacy policy live before launch, DPA template, per-workspace data-export endpoint, delete-on-request workflow, retention-policy config (default: 18 months for messages, configurable per workspace). Compliance is cheap pre-launch and expensive after.
  • I7 · AI cost ceiling per workspace. Claude classifies every inbound. ~$0.005 per call × 2,000 inbounds = $10/mo Claude cost on a $59/mo plan = 17% gross-margin hit. Plan a cheaper first-pass classifier (regex / embedding) and only fall back to Claude on ambiguous messages. Caps margins at ~$3–4/mo.
  • I8 · Setup Wizard should generate vertical landing pages. Mahmoud needs vertical SEO pages anyway. Have the Setup Wizard's vertical presets pre-write the marketing-site copy too. Reuses content, halves Mahmoud's load.
  • I9 · Sep 1 "launch" should be a private beta, not a public one. 2 founders + 5 design partners is not a public launch — it's a controlled rollout. Real public launch should be Oct 1 after 30 days of design-partner feedback. This is a positioning call, not a date slip: it lets Mahmoud build louder PR around Oct 1 with case-study numbers in hand.

Nice-to-have — V1.1 candidates

  • N1 · Slack/Discord integration for team mentions. Notify the team channel when an inbox conversation needs human attention. Saves switching apps.
  • N2 · Public-link booking page. Beyond the bot-initiated flow, give each workspace a /book/[slug] page customers can hit directly (like Calendly). Trivial off the existing slot generator.
  • N3 · Saved searches / smart inbox views. "Unread VIP" / "No-reply 24h" filters. Power-user feature.
  • N4 · Setup Wizard import. Let businesses paste their existing FAQ doc / Google Doc / website FAQ → AI auto-extracts the intents + replies + builds the library in one click. Big wedge.

04Best-in-Class Product Blueprint

If we get these 7 things right, the product will feel comparable to elite SaaS.

1 · Setup Wizard is the hero screen

5 steps · < 20 min · vertical preset autoload · live preview of how the bot will reply at each step · "skip to default" on every screen. Outcome: user is live before they get bored.

2 · Inbox feels live

New message lands → list updates without refresh · open thread auto-scrolls · soft "ping" sound for new messages in unattended conversations. Polling-based in V1, WebSocket V1.1. Outcome: feels like Intercom, not Gmail.

3 · The Contact record is a real CRM record

All channels merged. Full timeline (messages + bookings + tag changes + rule firings). Editable tags inline. Private notes inline. Status changeable in two clicks. Outcome: customer support reps don't need a second tool.

4 · The bot has personality

Each workspace defines an AI persona name (e.g. "Sara — your AI receptionist"). Bot identifies itself in first replies. Owner can configure "AI is replying / Human is replying" badge visibility. Outcome: customers don't feel tricked.

5 · Booking is one tap

Bot sends an interactive-list message (WA / IG native widget). Customer taps a slot. That's it. Confirmation auto-sent. Owner gets email. No extra clicks, no extra forms.

6 · The dashboard answers one question fast

"Is the AI making me money this week?" 6 cards above the fold: messages handled, bookings made, conversion rate, response time avg, handoffs, top-asked intent. Date-range toggle. No clutter.

7 · The brand promise — "Fix it once, runs forever"

The whole value-proposition lives in this line. Owner sets up the FAQ Library + Calendar once. The bot, the reminders, the CRM, the follow-up rules all run themselves. Setup-cost is paid upfront, value compounds for years. This is what makes us cheaper than a 2nd front-desk hire in months, not years.

Six top-level destinations. Inbox is home. Settings + Billing + User are bottom-pinned.

Core user flows

Onboarding (Day 0)

  1. Clerk signup (email + password OR Google OAuth)
  2. Workspace creation: business name + vertical dropdown
  3. Plan select: Starter / Growth (Growth pre-selected) — 14-day trial, no card
  4. Land on Setup Wizard (auto-opens, can't skip on first session)
  5. Wizard completes → land on Inbox with seeded demo conversation

Setup Wizard (5 steps · <20 min target)

  1. Business info — name, vertical (preset library autoloads), language(s)
  2. Working hours — weekly schedule editor (defaults to Mon–Sat 9–6)
  3. Services / catalog — 3–8 items with duration + price (preset autoloads)
  4. FAQ Library — review & edit 12–15 preset replies (intent + reply text)
  5. Connect channels — WhatsApp first (mandatory), IG + Messenger optional

Each step has Skip and Use Defaults buttons. Progress bar across top.

Inbox flow (the workhorse)

  1. Left rail: filters (All · Unread · Assigned to me · Handoff · Closed)
  2. Conversation list: 1 row per Contact (not per Conversation). Latest message preview, unread badge, channel icons stacked.
  3. Open thread: message history, channel-aware bubbles, reply box.
  4. Right panel (collapsible): contact card (name, channels, tags, status, notes button, link to Contacts page).
  5. Top bar of thread: assign · tag · close · "Hand back to AI" toggle.

Booking flow (customer-facing)

  1. Customer DMs intent matching BOOK
  2. Bot replies with WA interactive list of next 5 free slots
  3. Customer taps a slot
  4. Bot confirms in-chat + sends confirmation message
  5. Owner gets email · Appointment row created in DB · slot marked BOOKED
  6. Cron sends reminder N hours before (configurable per workspace)

Screen inventory (V1, 17 screens)

  • Auth: Signup · Login · Workspace creation · Plan select (4 screens)
  • Setup Wizard: 5 wizard steps + completion summary (6 screens)
  • App: Inbox · Contacts list · Contact detail · Calendar · Chatbot config · Automations · Analytics (7 screens)
  • Settings: Workspace · Team · Channels · Billing (within settings, modal/sub-page)
  • Empty + Error states: 6 distinct (no contacts yet, no appointments, no messages, no rules, no internet, 500)

Responsive strategy

  • Desktop (1280px+): three-pane inbox, full nav rail visible.
  • Tablet (768–1279): two-pane inbox (list collapsed to icons), nav rail collapsed to icons.
  • Mobile (<768): single-pane stack. Conversation list → tap → thread (back arrow). Native mobile app is V2; the web app must feel good on mobile because owners check inbox from their phones constantly.

Loading + empty states (the often-missed details)

  • Skeleton loaders on the conversation list and contact detail (not spinners — skeletons feel faster)
  • Empty inbox (Day 0): the demo conversation is already seeded so it's never truly empty
  • Empty Contacts: CTA "Connect a channel" or "Add manual contact"
  • Empty Calendar: CTA "Set working hours" linking back to Setup Wizard
  • Empty Automations: 3 "Suggested rules" cards the owner can apply in 1 click
  • Empty Analytics: explainer "Stats populate as messages flow in"

07Design-System Recommendations

The product must feel Linear / Vercel — not 2015 admin-dashboard.

Foundations

  • Type: Inter (free) or Geist (Vercel's font, free). One typeface only.
  • Type scale: 12 / 13 / 14 / 16 / 20 / 24 / 32. Six steps, no more.
  • Spacing: 4-pt base scale (4, 8, 12, 16, 24, 32, 48, 64).
  • Colors: brand teal + neutral grays + 3 semantic (success / warn / danger). 8 total + dark mode mirror.
  • Radii: 8 / 12 / 16. No more.
  • Shadows: 2 levels (subtle + medium). No drop-shadow soup.

Component library

  • shadcn/ui as the base. Install only what we use; don't bloat.
  • Components needed in V1: Button (4 variants), Input, Textarea, Select, Dialog, Sheet, Dropdown, Tabs, Toast, Card, Avatar, Badge, Tag, Skeleton, EmptyState, DataTable, Tooltip.
  • Custom V1 components (~7): ConversationListItem, MessageBubble, ChannelBadge, ContactCard, BookingSlotPicker, FaqEditor, RuleBuilder.
  • Lucide-react for icons. One icon set only.
  • Dark mode from Day 1 (Tailwind class-based). Not optional in 2026.

Motion

  • Use motion sparingly. 150–250ms ease-out on hover / active. Page transitions are off.
  • New-message "ping" sound: subtle, mutable per workspace, disabled by default for first 24h.
  • Confetti / celebrations on first booking received. One-time per workspace.

Voice & tone

  • Empty-state copy is human, not corporate. "Nothing here yet — your first DM will land here" not "No data available."
  • Error messages are honest. "We couldn't send this — Meta returned 'too many requests'. Try again in 30s." Never "Something went wrong."
  • Notifications are useful, not loud. Default to email + in-app, not push.

Missing abstractions (build these in Week 1)

Security checklist (pre-launch)

  • ☐ Stripe webhook signature verification
  • ☐ CSRF protection on all mutation routes (Next.js App Router does this by default for Server Actions)
  • ☐ Rate limit on auth endpoints (10/min/IP), webhook endpoints (100/min/source)
  • ☐ All secrets in Vercel env, none in repo
  • ☐ Sentry doesn't leak PII (filter email, phone, message bodies)
  • ☐ Signed URLs for attachments (15-min expiry)
  • ☐ DB access via service-role only — no anon access

09Database Review

The current schema is a good start. Here's what's missing and what to tighten.

Tables to add (V1)

// 1. Membership (multi-user per workspace, roles)
model WorkspaceMember {
  id          String   @id @default(cuid())
  workspaceId String
  userId      String
  role        Role     @default(MEMBER)  // OWNER | ADMIN | MEMBER | VIEWER
  invitedAt   DateTime @default(now())
  acceptedAt  DateTime?
  workspace   Workspace @relation(fields: [workspaceId], references: [id], onDelete: Cascade)
  @@unique([workspaceId, userId])
  @@index([workspaceId])
  @@index([userId])
}

// 2. Subscription & quota tracking
model Subscription {
  id                    String    @id @default(cuid())
  workspaceId           String    @unique
  stripeCustomerId      String?
  stripeSubscriptionId  String?
  plan                  Plan      @default(STARTER)
  status                SubStatus @default(TRIALING)
  trialEndsAt           DateTime?
  currentPeriodStart    DateTime
  currentPeriodEnd      DateTime
  contactsLimit         Int
  contactsUsed          Int       @default(0)  // billable contacts this period
  extraContactPacks     Int       @default(0)  // total from top-ups
  cancelAtPeriodEnd     Boolean   @default(false)
  updatedAt             DateTime  @updatedAt
  workspace             Workspace @relation(fields: [workspaceId], references: [id], onDelete: Cascade)
  @@index([stripeCustomerId])
  @@index([currentPeriodEnd])
}

// 3. Audit log (compliance + debugging)
model AuditLog {
  id          String   @id @default(cuid())
  workspaceId String
  actorId     String?  // userId, or null for system
  action      String   // "appointment.created", "rule.toggled", etc.
  targetType  String?  // "Contact", "Appointment", ...
  targetId    String?
  metadata    Json?
  ipAddress   String?
  userAgent   String?
  createdAt   DateTime @default(now())
  @@index([workspaceId, createdAt(sort: Desc)])
  @@index([targetType, targetId])
}

// 4. Webhook idempotency & replay log
model WebhookDelivery {
  id            String    @id @default(cuid())
  channel       Channel
  externalId    String    // channel-native message id
  payload       Json
  receivedAt    DateTime  @default(now())
  processedAt   DateTime?
  errorMessage  String?
  retryCount    Int       @default(0)
  @@unique([channel, externalId])  // idempotency key
  @@index([processedAt])
}

// 5. Message attachments
model MessageAttachment {
  id          String   @id @default(cuid())
  messageId   String
  workspaceId String
  url         String   // R2/S3 path
  mimeType    String
  filename    String?
  sizeBytes   Int
  createdAt   DateTime @default(now())
  message     Message  @relation(fields: [messageId], references: [id], onDelete: Cascade)
  @@index([messageId])
  @@index([workspaceId])
}

// 6. Channel link (one Contact ↔ many channel handles)
model ChannelLink {
  id          String   @id @default(cuid())
  contactId   String
  workspaceId String
  channel     Channel
  externalId  String   // phone for WA, IG handle for IG, etc.
  primary     Boolean  @default(false)
  contact     Contact  @relation(fields: [contactId], references: [id], onDelete: Cascade)
  @@unique([workspaceId, channel, externalId])
  @@index([contactId])
}

// 7. AI classification log (cost & quality tracking)
model ClassificationLog {
  id           String   @id @default(cuid())
  workspaceId  String
  messageId    String
  intent       String?
  confidence   String   // "high" | "low"
  promptTokens Int
  outputTokens Int
  cachedHit    Boolean  @default(false)  // for embedding-cache fallback
  createdAt    DateTime @default(now())
  @@index([workspaceId, createdAt])
}

Multi-tenant safeguards

  • Postgres RLS on every workspace-scoped table. Policy: USING (workspace_id = current_setting('app.workspace_id')::text). Set the setting from middleware on every request.
  • Cascade deletes from Workspace down. If a workspace is deleted (rare but possible), everything goes with it.
  • Soft delete on Contact (add deletedAt) — keeps audit history but excludes from queries via Prisma middleware.
  • Workspace.timezone (IANA string, e.g. "Africa/Cairo"). Required field. Everything date-aware uses it.

Data retention strategy

  • Messages: 18 months default, configurable per workspace (down to 6 months for privacy-conscious customers; up to "forever" on Enterprise).
  • Audit logs: 12 months. Older rows moved to cold storage or deleted.
  • WebhookDeliveries: 30 days. After that, idempotency is moot.
  • Deleted workspaces: 30-day soft-delete window for accidental delete; hard-delete cron after.
  • Customer data export endpoint (GET /api/workspace/export): returns a zip of all Contacts + Conversations + Messages + Appointments as JSON. Required for GDPR.

∑The 10 founder-level calls I'd make today

If you only read one section of this doc, read this. These are the decisions that compound over the next 6 months.

  1. Drop TikTok from V1. Ship in V1.1. Buys 3–5 dev-days, no material lost value.
  2. Vertical presets are mandatory, not optional. The Setup Wizard must ship pre-filled. This is the single biggest churn lever in V1.
  3. Define "billable contact" precisely before any code is written. My recommendation: unique person you sent ≥ 1 outbound message to this month.
  4. Add the 7 missing schema tables in Week 1 (WorkspaceMember, Subscription, AuditLog, WebhookDelivery, MessageAttachment, ChannelLink, ClassificationLog). Cheap now, expensive to retrofit.
  5. Postgres RLS from Day 1 as defense-in-depth on top of middleware filtering. One forgotten where workspaceId = a tenant leak.
  6. Real-time inbox via SWR polling in V1. No WebSocket infra needed yet; upgrade later.
  7. Position Sep 1 as a private beta launch, public launch Oct 1. Same engineering deadline, way better marketing story (case-study numbers in hand by Oct).
  8. Cheap pre-classifier before Claude. Regex / keyword matching catches 30–40% of clear intents (hours, pricing, location). Saves Claude calls and protects gross margin.
  9. Demo data on signup. A new workspace must never see a fully empty inbox. Seed a guided demo conversation.
  10. Stripe billing + plan gating in Week 9, not Week 10. Don't underestimate billing — it's a full sprint to do right (webhook hardening, plan-gate matrix, trial countdown, reconciliation cron). Allocate the time.
